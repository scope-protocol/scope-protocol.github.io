SCOPE · design choice · stealth payments

Who creates the one-time account?

Each stealth payment lands in a fresh token account. Whoever can create that account first controls how it is set up, so only the right party should be able to. There are two sound ways to do it. This page lays them side by side, with no pick.

Terms

Epayer's one-time public key for a payment, published in the announcement. Also called R.
Sshared secret. The payer computes it from its secret for E, the recipient from E and its scan key. Nobody else can.
Pone-time owner key. Only the recipient can sign as P.
Announcementsmall on-chain record the recipient scans for by its 1-byte tag.

The two options

OPTION A · PAYER AS BASE 
address = create_with_seed(payer, hash(E))
creator signs as: payer
announcement: tag, E, payer

The address comes from the payer's key and E. Creating it needs the payer's signature, so only the payer can.

OPTION B1 · SHARED-SECRET KEY 
a = derived from S,  A = a·G
address = A
creator signs as: A
announcement: tag, E, payer

The address is a key both sides derive from S. Creating it needs a signature from a, so only someone who knows S can: the payer or the recipient. A variant, create_with_seed(A, hash(E)), behaves the same.

What stays the same

  • Front-running is blocked. Creating the account needs a signature an outsider can't make.
  • Privacy is the same. The payer signs the payment transaction either way, so the payer is public in both.
  • The payer gets the rent back. Both keep the payer in the announcement so reclaim knows where to send it.
  • Announcement size is the same, about 68 bytes.
  • One atomic transaction per side: create, configure, hand over to P, announce, fund, transfer.
  • Scanning starts the same way: filter announcements by the 1-byte tag.
  • Rent stays locked until the recipient sweeps. That comes with any one-time account.

When each one fits

A fits when

  • recipients always know who paid them, as in payroll or invoices
  • you want the program itself to reject a payment announced with the wrong E
  • one signature per payment and standard wallet signing matter

B1 fits when

  • a recipient may get E from somewhere that doesn't say who paid
  • scanning should reject non-matching tags without an account read
  • copied announcements should be impossible, not just detectable

Checks before choosing B1

  • A transaction signed with a key derived from a raw scalar verifies on Solana. Expected, since the signature is standard Ed25519, but not yet tested.
  • If someone sends lamports to address A first, plain create fails. The fallback (transfer, allocate, assign) must work when signed by a.

Option A's equivalents are covered: create_with_seed only allocates when the base signs, and the same fallback applies.

The deciding question

Will a recipient ever have E for a payment without knowing who paid?

If yes, only B1 lets them find it. If no, the choice comes down to the smaller trade-offs above: fewer reads and no copied announcements in B1, against an on-chain check of E and one signature in A.
