1. Project

SCOPE is a confidential payout rail on Solana. A visible payer pays many recipients with encrypted amounts; a stealth recipient gets a fresh one-time account per payment that the public cannot tie to them. Funds stay ordinary Token-2022 tokens: no pool, no relayer, no custody. One Pinocchio program with two handlers, never in the funds path; one Rust CLI for both sides.

3. MVP use cases

1 use case = 1 atomic state transition = 1 instruction handler (Pinocchio, not Anchor).

Use caseHandlerSignerStatement
UC1announcePayerPublish a one-time token account the payer created, configured and handed to the recipient's key P, so the recipient can find it. Announcement PDA: none → 68-byte record.
UC2reclaimnone (any caller)Close an emptied one-time account and its announcement; both rents return to the payer. Announcement and token account: open → closed.

4. Granularity self-check

RuleResult
1 AtomicityPass. UC1 is only announce, UC2 only reclaim. Setup, funding and the sweep are Token-2022 and System instructions, not ours; the client, not the program, keeps setup, announce and transfer in one transaction.
2 State ownershipPass. The only program-owned state is the announcement PDA; token accounts belong to Token-2022. Scan reads announcements over RPC, with no indexer.
3 Real signersPass. The payer signs UC1 and the program checks it. UC2 has no signer by design: the refund can only reach the payer stored in the announcement.
4 On-chain vs clientPass. On chain: the checks, the record, the close. Client: key derivation, proofs, journal, scan, sweep, fresh-destination policy (client-only).

5. AI red team

Run after sections 3 and 4. Three findings accepted, four rejected with the reason.

AI findingOur verdictWhat changed
reclaim can close an announced account before it is funded, if announce and the transfer are sent in separate transactions.Accepted. No funds are lost (a late transfer fails), but it is a griefing window.New client rule CL02: announce and the transfer always share one transaction.
The self-check says setup and announce are 'in the same transaction' as if the program enforced it.Accepted. The program checks the account's state, not the transaction shape.Rule 1 wording now names this as a client guarantee.
Signers are not listed for the whole flow: P and a fee payer sign the sweep, the PDA signs the close CPI.Accepted.Actors table lists P and D_owner; the end-to-end diagram marks every signer.
The journal plus scan is an undeclared off-chain indexer (rule 2).Rejected. The journal holds no protocol state: the chain decides what landed. Scan reads chain state directly.None; the RPC dependency is drawn as an external service.
reclaim bundles two state changes, the token-account close and the announcement close.Rejected. One handler, one transition: the payment goes from open to closed, atomically.None.
The view tag is on-chain data that only a client uses, blurring rule 4.Rejected. Rule 4 separates logic, not data; scan needs the byte on chain to filter by memcmp.None.
REQ12 overstates: 'any balance' including confidential balances is Token-2022 behaviour, untested here.Rejected. Two tests cover it, one with a pending confidential balance (reclaim_fails_while_balance_remains, refuses_while_confidential_balance_is_pending).None.
